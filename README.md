# X_Finder

カメラマン募集のポストを X から集め、点数を付けて、スマホの Web ページ「X Finder」で確認するための仕組みです。
今の仕組み(x-search-pipeline)を作り直したもので、しばらくは両方を並行して動かします。

モジュールの番号(N0〜N15)と用語は、定義書に合わせています。

## いまできること(第1段階: 収集と保存 / 第2段階: AI 判定と採点)

| 番号 | 名前 | 場所 |
| --- | --- | --- |
| N1 | 設定読込 | `finder/config.py`(Notion 8表と【9】絵文字の一覧から読む。不正な値は前回の値を使う) |
| N2 | 収集 | `finder/collect.py`(TwitterAPI.io。失敗したら検索時間枠を進めない) |
| N3 | 一次フィルタ(一部) | `finder/filters.py`(リポスト・フォロワー数・入りきらなかった除外語。減点語は記録だけ) |
| N12 | データ保存 | `finder/store.py`, `schema.sql`(Cloudflare D1) |
| N15 | ユーザー台帳 | `finder/store.py`(投稿者・引用元・メンション先・リプライ先を登録) |
| N4 | AI 判定 | `finder/judge.py`(文字だけを Claude Haiku 5.5 でまとめて判定。Gemini にも切り替え可。対象外にするかはルールで決める) |
| N13 | X Finder | `web/`(Cloudflare Workers。D1 は読むだけで、書くのは案件カードの確認の状態だけ。Cloudflare Access を通った人だけ見られる) |
| N10 | 採点 | `finder/score.py`(【5】点数表と【6】クリティカル条件。都道府県が分かれば地名の減点語は使わない) |

収集は Cloudflare Worker(`trigger/worker.js`)が 10分ごとに Collect ワークフローを起動して動き、判定待ちが「まとめて判定する件数」たまるか、いちばん古いポストが「判定を待つ最長時間(分)」待ったら判定・採点します。案件カードは「未確認(一度も開いていない)/ 確認済み / 保留(ピン留め。2週間を過ぎても残る)/ 削除予定」で分けて見られます。カードを左右にスワイプしても状態を付けられ、どちらの向きで何を付けるかは設定(左上の「X Finder」)で変えられます(初期値は右=保留、左=削除予定)。削除予定の案件は、収集の実行のたびに、投稿日から14日たったものを D1 から消します(ユーザー台帳は残します)。右上の今月の費用をタップすると、累計の判定数、1日あたりの取得ポスト数と費用、今月と先月の比べ、案件の種類・都道府県の内訳などのサマリーが見られます。スパムや虚偽の申告をしているクライアント、被写体ではなくカメラマンだった人は、案件の詳細から「ブラックリスト」に入れられます。入れた人のポストはこれまでの分もこれからの分も X Finder に出さず、AI の判定にもかけません(設定から解除でき、解除すると直近14日の分は判定待ちに戻ります)。一覧のいちばん上で下に引っぱると再読み込みします。下へスクロールすると上部がたたまれ(状態タブは数字と色だけ、絞り込みは隠れる)、上へ戻すと広がります。開いた詳細は、一番上で下へ引っぱると閉じます。詳細の本文をタップすると X アプリでそのポストが開き、いちばん下のボタンは「とじる」「保留にする」「ブラックリストにいれる」「削除予定にする」の4つです(ブラックリストは削除予定と同じ赤)。画面上の ↻ ボタンはなくし、再読み込みは一番上で引っぱって行います。設定は左上の「X Finder」を押すと開き、画面の色(白・黒・システムに合わせる)を選べます(この端末に保存)。設定の「データベース」から、ポスト・AI の判定・ユーザー台帳・費用などの表の中身を新しい順に見られます(検索可、見るだけ)。判定で対象になった案件に画像が付いていれば、Claude Haiku がメンバー表などに載っている X のアカウントを読み取り(1 ポスト 1 回だけ、`finder/image_step.py`、D1 の `image_reads` 表)、詳細の「関係するアカウント」に「画像から」として並べます。Google カレンダーの「iCal 形式の非公開 URL」をリポジトリの secret `GCAL_ICS_URL` に登録すると(公開のたびに Worker の secret に入ります)、AI が読み取った撮影日にすでに予定があるかを一覧に「予定あり / 空き」、詳細にその日の予定として出します(`web/src/calendar.js`、予定は保存しません)。予定名に「休み」「有給」などの言葉(【7】基本設定の「休みとみなす予定の言葉」)が入っている予定は予定ありに数えず、一覧に「休み」と出します。依頼主のプロフィール(名前・自己紹介・所在地)から、年齢(「18↓」「30↑」「成人済み」「義務教育修了済み」「高校生」など、矢印や記号の書き方はいろいろ読む)と活動地域(「関西」「東海」などの地方、都道府県、名古屋・札幌などの市)を読み取り、カードの依頼主の名前の横に出します(`web/src/profile.js`、AI は使わない)。プロフィールに書いてないときは、プロフィールの URL 欄や自己紹介にあるリンク先(Litlink など)のページの文字からも同じように読み、詳細に「リンク先から」と出します(案件になった依頼主だけ、収集のときに 1 人 1 回ページを読んで D1 の `user_links` 表に文字を保存し、30日たったら読み直す。`finder/link_step.py`)。ホームの「まとめて」から、いま見ているタブの案件を言葉(作品名・イベント名・場所など)や条件(首都圏以外・活動地域が首都圏以外・カレンダーで予定あり)で絞って選び、まとめて削除予定・保留・確認済みなどにできます(元に戻せます)。通知は次の段階で作ります。

## 準備(初回だけ)

### 1. Repository secrets に鍵を入れる

GitHub の X_Finder → Settings → Secrets and variables → Actions → New repository secret で、次の名前で登録します。

| 名前 | 中身 |
| --- | --- |
| `TWITTERAPI_KEY` | TwitterAPI.io の API キー(今の仕組みと同じもの) |
| `ANTHROPIC_API_KEY` | Claude の API キー(判定に使う。ないと判定だけ飛ばす) |
| `GEMINI_API_KEY` | Gemini の API キー(【7】基本設定で Gemini に切り替えたときだけ必要) |
| `NOTION_API_KEY` | Notion のインテグレーションのキー(今の仕組みと同じもの) |
| `NOTION_PARENT_PAGE_ID` | 新しい 8表を置く Notion ページの URL |
| `NOTION_KEYWORDS_DB_ID` ほか3つ | 今の 4表の ID(今の仕組みと同じ名前・同じ値。移行にだけ使う) |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare のアカウント ID |
| `CLOUDFLARE_API_TOKEN` | D1 の編集権限を持つ API トークン |
| `D1_DATABASE_ID` | 作った D1 データベースの ID |

### 2. Setup ワークフローを上から順に実行する

Actions → Setup → Run workflow で、task を選んで 1 回ずつ実行します。

1. `d1_schema`: D1 にテーブルを作る
2. `notion_tables`: Notion 8表を作る(親ページにインテグレーションを招待しておく)。あとから足した表(【9】絵文字の一覧)も、もう一度実行すればその表だけ作られる
3. `migrate_preview`: 今の 4表からの振り分け案を見る(何も書き込まない)
4. `migrate_apply`: 振り分け案のとおりに新しい表へ移す(今の 4表はそのまま残る)

### 絵文字の一覧(【9】)

VTuber などはキャラ名の代わりに決まった絵文字(推しマーク)で書かれることがあります。
【9】絵文字の一覧に「絵文字・キャラ名・グループ」を入れておくと、判定のときにポストの本文から一覧の絵文字を探し、
その意味を AI に渡します。AI はそれを見て、作品・キャラ欄にキャラ名を書きます(同じ絵文字に何人かいるときは本文の流れから選ぶ)。
表を初めて作るときの中身は `data/emojis.tsv`(タブ区切り)です。作ったあとは Notion の表を直接直してください。

### 場所の判断とイベントの一覧(【10】)

撮影の場所(都道府県)は、次の順で判断します。カードの場所の横に、どれで判断したかが出ます。

1. 本文・引用元の本文に書かれた地名・会場名
2. 【10】イベントの一覧: 本文に略称(何通りでもカンマ区切り)があれば、その開催地を AI に渡す。会場が回ごとに変わるイベントは、都道府県を「毎回ちがう」にする
3. 添付画像: 対象になった案件の画像を読むときに、会場・イベント名・都道府県も読む。1・2 で分からなかった案件だけ、画像の場所に置き換えて点数を計算し直す
4. 投稿者プロフィールの地域・自己紹介(「推定」と表示)

表を初めて作るときの中身は `data/events.tsv` です(よく知られたイベントの下書き)。

### 3. Collect ワークフローを試す

Actions → Collect → Run workflow で、まず `dry_run`(何も保存しない)を実行し、結果の要約を確認します。
問題なければ `production` で実行します。定刻での自動起動は、手動で数回試したあとに追加します。

### 4. 10分ごとの自動起動(N0)を Cloudflare に置く

1. GitHub → Settings → Developer settings → Fine-grained tokens で、Repository access を X_Finder だけ、Permissions の Actions を Read and write にしたトークンを作る
2. Cloudflare → Workers & Pages → 作成 → Worker を作り(名前は `x-finder-trigger`)、コードの編集で `trigger/worker.js` の中身を貼り付けてデプロイする
3. その Worker の 設定 → 変数とシークレット に、`GITHUB_TOKEN`(種類はシークレット)として 1 のトークンを入れる
4. 設定 → トリガー → Cron トリガーに `*/10 * * * *` を追加する

### 5. X Finder(N13)を公開する

1. Cloudflare の API トークン(`CLOUDFLARE_API_TOKEN`)に、権限「アカウント / Workers スクリプト / 編集」を足す
2. Actions → Deploy Finder → Run workflow で公開する(以後は main の `web/` が変わるたびに自動で公開される)
3. Cloudflare → Workers & Pages → `x-finder` → 設定 → ドメインとルート で、workers.dev の「Cloudflare Access」を有効にする(自分のメールアドレスだけ許可)
4. Zero Trust → Access → アプリケーション → `x-finder` の「アプリケーション対象者 (AUD) タグ」と、Zero Trust の チーム名(`○○.cloudflareaccess.com`)を、`x-finder` の 設定 → 変数とシークレット に `ACCESS_AUD` と `ACCESS_TEAM_DOMAIN` として入れる

Access の確認ができないあいだは、ページは何も表示しません。
